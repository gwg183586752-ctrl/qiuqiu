# 足球数字人基线与 M0 总规格

## Problem Statement

用户希望在自己的 Windows 电脑上，与具有声音、表情和动作的小糖交流，并在刷新后继续聊，同时验证大模型能真正调用工具。课程材料描述的是对已有应用进行升级，当前项目却没有可运行的数字人；直接执行课程改造任务会缺少语音、演出和协议基线。

即使补齐演示，只有单一全局会话、一问一答模型和无鉴权连接，也不能满足双浏览器隔离、可靠续聊及后续工具扩展。需要先建立可复现的基线，再用清晰的会话、回合与工具边界完成 M0。

## Solution

提供只在本机运行的完整浏览器数字人应用。用户点击开始录音，再点击结束并发送，小糖以冰糖音色逐句回答，配合基础口型、字幕、表情和四个动作。首版使用可替换的官方 VRM 验证形象，保持小糖的足球迷人设。

同一浏览器可以续聊，新标签页接管原会话，不同浏览器保持独立。只有完整生成并保存的问答进入历史；工具查询过程显示状态，获得结果后才口播有效回答。M0 通过时间探针验证 Agent，最多尝试三次工具再收尾，并留下可查询的回合与性能证据。

## User Stories

1. **US-01** 作为本机演示者，我希望按明确说明启动应用，从而能重复演示。
2. **US-02** 作为维护者，我希望启动前发现缺失配置，从而避免演示中才发现关键凭证未配置。
3. **US-03** 作为维护者，我希望区分关系存储和向量扩展的诊断结果，从而知道哪些问题真正阻塞 M0。
4. **US-04** 作为用户，我希望看到数字人、状态、当前字幕和录音按钮，从而知道现在能做什么。
5. **US-05** 作为用户，我希望点击开始、再点击结束发送语音，从而明确控制自己的发言边界。
6. **US-06** 作为用户，我希望系统理解真实录音，从而获得针对我所说内容的回复。
7. **US-07** 作为用户，我希望麦克风不可用或没有说话时得到提示，从而知道如何重试。
8. **US-08** 作为用户，我希望小糖思考和说话时暂停录音，从而避免叠加回合或误录她的声音。
9. **US-09** 作为用户，我希望听到连续的冰糖音色回复，从而自然理解回答。
10. **US-10** 作为用户，我希望字幕对应正在播放的句子，从而不会看到与声音不同步的内容。
11. **US-11** 作为用户，我希望小糖说话时有基础口型和表情，从而感受到数字人在交流。
12. **US-12** 作为用户，我希望小糖通过点头、摇头、歪头和前倾表达，从而得到课程要求的演出体验。
13. **US-13** 作为用户，我希望内部控制标签不出现在声音或字幕里，从而获得自然的表达。
14. **US-14** 作为用户，我希望首次浏览器阻止播放时能明确激活声音，从而顺利开始对话。
15. **US-15** 作为用户，我希望新会话播放固定开场白，从而知道小糖已经准备好。
16. **US-16** 作为返回用户，我希望刷新和重新打开后直接继续聊，从而不重复听开场白或历史音频。
17. **US-17** 作为本机演示者，我希望缺少或错误口令的连接被拒绝，从而校验演示入口。
18. **US-18** 作为维护者，我希望云密钥和连接口令不进入前端错误和日志，从而避免暴露凭证。
19. **US-19** 作为用户，我希望两个浏览器各自聊天，从而不会串话或听到对方的回答。
20. **US-20** 作为返回用户，我希望服务重启后仍能续聊，从而不丢失已完成的问答。
21. **US-21** 作为用户，我希望小糖记住最近十二条完整消息，从而支持连续交流。
22. **US-22** 作为同浏览器用户，我希望新标签页接管原会话，从而自然切换交谈页面。
23. **US-23** 作为旧页面用户，我希望看到会话已转移且不反复重连，从而避免两个页面抢占。
24. **US-24** 作为用户，我希望刷新时取消未完成回合，从而不把半句回复带入之后的对话。
25. **US-25** 作为用户，我希望完整生成并保存的回答即使没听完仍被记住，从而保持已完成上下文。
26. **US-26** 作为用户，我希望旧回合迟到的声音和文字被丢弃，从而不打断新会话页面。
27. **US-27** 作为维护者，我希望重复回合请求不会重复执行和保存，从而避免多份回复与重复云调用。
28. **US-28** 作为演示者，我希望真实模型调用时间探针后回答，从而证明工具循环确实存在。
29. **US-29** 作为用户，我希望工具失败或反复请求时最终能收尾，从而不会一直等待。
30. **US-30** 作为维护者，我希望每轮最多实际尝试三次工具且失败计数，从而控制循环和调用成本。
31. **US-31** 作为用户，我希望查询时看到状态、结果回来后听有效回答，从而分清等待与答案。
32. **US-32** 作为足球爱好者，我希望和小糖聊基础规则及历史背景，从而获得有趣且谨慎的交流。
33. **US-33** 作为足球爱好者，我希望实时信息尚未接入时被明确告知，从而不会相信编造比分。
34. **US-34** 作为用户，我希望 Agent 改造后仍保持小糖原有表达规则，从而保留熟悉的语音演出。
35. **US-35** 作为维护者，我希望按会话或回合查询输入、结果、工具和耗时，从而定位异常。
36. **US-36** 作为维护者，我希望成功、失败与取消记录明确区分，从而不把终止回合当作成功。
37. **US-37** 作为维护者，我希望附加日志写入失败不撤销已经成功的问答，从而避免重复业务。
38. **US-38** 作为演示者，我希望在同一电脑同条件下比较基线与 Agent，从而知道真实新增延迟。
39. **US-39** 作为开发者，我希望通过公开协议和可控云模拟验证行为，从而在不付费调用的日常检查中发现回归。
40. **US-40** 作为验收者，我希望真实声音、角色、工具和延迟都有独立证据，从而知道哪些能力实际可用。
41. **US-41** 作为维护者，我希望存储升级失败时保留既有数据并拒启，从而能安全恢复。
42. **US-42** 作为后续开发者，我希望已有可插工具的大脑、持久会话与预留数据结构，从而继续 M1—M3 时有明确起点。

## Implementation Decisions

- 在 dev 主工作区从零建立单包 TypeScript 应用，先基线、后 M0；不复用另一条设计路线作为现有代码。
- 采用 React、Three.js/VRM、Node 原生 HTTP/WebSocket 与 MiMo 云接口；角色使用官方样例 v1.0.1 并保留许可证信息，最终造型后换。
- 前后端按录音、连接、播放、演出、网关、会话、回合、云适配器、Agent、存储和审计划分职责。
- 运行时和精确依赖版本按实机核定，不能把作者 Node 24 或模型权限当作本机事实。
- 首版仅本机回环访问，共享口令在握手阶段校验；不引入账号体系。
- 会话由服务端生成标识，同源浏览器保存；单会话单活跃页面，使用连接代次拒绝旧任务提交。
- 完整问答和回合成功状态原子保存，随后宣告完成；播放完成独立控制前端能否录音。
- 一对普通消息属于一个回合；续聊取最近 12 条完整消息，固定开场白不挤占该窗口。
- 原生 SQLite 使用版本化迁移，并预留消息打断、知识块、实体和审计结构；向量诊断失败不伪称通过，也不自动阻塞 M0 会话。
- 大脑的消息输入、可展示增量输出和取消边界稳定；优先通过真实 spike 选择 AI SDK 6 或同构手写实现。
- 工具阶段不口播过程文本，执行层限制三次实际尝试；最终回答阶段移除工具定义，仍允许增量回复。
- 人设保留六条演出规则；M0 仅时间探针，知识与实时能力说明随实际注册工具调整。
- SQLite 回合终态作为审计依据，JSONL 是附加出口；指标区分服务端首字、首音就绪与浏览器实际首音。
- 浏览器自动播放处理、录音合法格式、消息身份和提交去重，是为实现已确认行为补齐的工程设计；它们不代表原版课程代码已经存在。

## Testing Decisions

- 好测试检查用户或协议消费者可观察的行为，不绑定内部类、方法顺序或实现细节。
- 主测试接缝拟采用真实 WebSocket 边界：真实网关、真实临时存储、可控 fake 云接口。覆盖鉴权、会话、回合完成、接管竞态、工具次数和审计结果。
- 少量浏览器验收检查录音状态、音频激活、字幕音频排序、过期事件清理及基础演出；浏览器效果不能仅由服务端事件单测证明。
- 真实云测试单独证明模型权限、录音格式、音质、时间探针、流式工具协议与延迟；不将 fake 测试结果当作真机证据。
- 故障覆盖空录音、权限拒绝、数据库事务失败、JSONL 出口失败、工具异常、超时、TTS 中断、重复请求及旧连接晚关闭。
- 当前没有已有应用测试；课程提出的 node:test 与 fake adapter 是参照方案，不能称为本仓已有实现。
- 每个细节任务同时交付自己的行为验收；最后进行跨任务回归，不把所有测试集中留到收尾。
- 测试接缝与任务粒度随本地草案提交审阅，尚未将待审任务发布为 ready-for-agent。

## Out of Scope

- 公网或局域网交付、账户注册登录、多租户权限。
- 知识摄取、RAG、实时比分/赛程/积分接口。
- 用户说话打断、连续自动监听、下一条录音排队、未完成回合后台续跑。
- 庆祝/惋惜新动作、最终小糖外观、精准中文音素口型、逐字字幕。
- 聊天记录列表、跨浏览器账号级历史同步。
- Python 本地模型、Docker、ORM、额外后端框架、完整遥测平台。
- 自动配置任务追踪器、自动发布工单、Git 提交或应用实现。

## Further Notes

这是根据已完成的讨论与 ADR-0001—0004 整理的 to-spec 总规格。对应六项能力的 SHALL 要求及 WHEN/THEN 场景负责细化行为，设计说明负责具体接缝，任务草案负责实施顺序；内容冲突时在本次 OpenSpec 变更内统一修订。

已有按量 API 账号不等于所有模型可用。精确模型、版本、超时和音频参数在实施验证票中核定；这些是具体且有退出条件的调查，不是重新“探索整个代码库”。向量扩展、真实 SDK 工具兼容性和声音效果尚未实测。

延迟保留相对基线增加不超过 500ms 的优化目标。超标应留下原始样本并归因，而非自动切换实现或隐藏失败；作者约 0.9 秒不直接用作本机基线。

项目未配置 issue tracker 和 triage 标签，当前没有父 issue。任务逐票作为本地草案供审阅；正式发布前须批准粒度/依赖，并配置或明确发布载体。
